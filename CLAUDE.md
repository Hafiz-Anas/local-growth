## Project

AI Growth Engine (shown to users; code, repo, DB and cookie names keep "local growth" / `lge_`) — Instagram growth/management app for local businesses (Raid Technologies). Next.js 16 + PostgreSQL/Prisma + Auth.js; every screen reads and writes through the JSON API with TanStack Query. Instagram data, AI generation, email and file storage sit behind swappable service interfaces with mock/local implementations until those integrations land. See README.md for setup and the real-vs-mocked list.

## Architecture

**Data flow.** Server pages in `app/` only guard (`requireFeature()` / `requireAdmin()`, → `notFound()`/redirect) and render a client `*View` from `components/<feature>/`. Views load data with the hooks in `lib/api/queries.ts` (user screens) and `lib/api/admin.ts` (admin), each with an Instagram-style skeleton, `ErrorState` and `EmptyState` (`components/shared/states.tsx`). The (user) layout renders the business view model (`getClientView()`, `lib/server/client-view.ts`) into `ActiveClientProvider`; after changing the business itself (photo, Instagram connection) call `router.refresh()`. Nothing under `app/`, `components/` or `lib/api` may import `/mock-data` — only the mock services, the seed and the front-end-only Gallery / AI chat (`mock-data/gallery`, see below) do.

**Auth.** Auth.js v5 (`auth.ts` at the root): Credentials provider + bcryptjs, JWT session in an httpOnly cookie. Session claims (`role`, `businessId`, `name`, `avatarUrl`, effective `features`, `sessionVersion`) live in the JWT. On **every** request the `jwt` callback runs `checkSession` (`lib/auth/claims.ts`, one PK lookup): deleted/suspended users and tokens whose `sessionVersion` differs are signed out; claims reload when `User.updatedAt` or `Business.permissionsUpdatedAt` is newer than the token (5-min safety refresh otherwise). Any code that changes a business's `FeaturePermission` rows must bump `permissionsUpdatedAt` (`lib/server/permissions.ts` does); any password change must go through `setPassword()` (`lib/server/passwords.ts`), which bumps `sessionVersion`. `authorize()` rate-limits failed logins (5 / 15 min per IP + email) through the `RateLimiter` interface (`getRateLimiter()` in `lib/server/rate-limit.ts`, in-memory; `RATE_LIMIT_STORE` selects the implementation) and throws `CredentialsSignin` subclasses whose `code` the login form shows. `lib/auth/actions.ts`: login, logout, start/exit admin preview. Password reset: `lib/server/password-reset.ts` + `app/api/password-reset/{request,confirm}` (SHA-256-hashed single-use token, 1 h), link sent via `EmailService` (`lib/services/email.ts`). Demo logins live in `config/demo.ts` (used by the seed and the login page).

**API (`app/api`).** Every route is wrapped in `handler()` (`lib/server/http.ts`): JSON envelope `{ ok: true, data }` / `{ ok: false, error: { code, message, details? } }`, `ApiError` for expected failures, Zod via `readJson` / `readQuery` / `readParams`. Guards in `lib/server/guards.ts`: `requireAuth`, `requireRole("ADMIN" | "USER")`, `requireBusiness`, `requireFeature(...keys)` / `requireAnyFeature` / `assertFeature` — a disabled feature is **404**, never 403. The businessId always comes from the session (or an admin route param), never from the body; lookups by id use `where: { id, businessId }` so other businesses' rows are 404. Queries use the explicit `*_SELECT` constants + mappers in `lib/server/dto.ts` so hashes/tokens are never loaded. Business-scoped reads live in `lib/server/data.ts` (shared by user routes and `/api/admin/preview/:id`); log changes with `logActivity()`. Response types: `types/api.ts`. Browser calls: `apiFetch` (`lib/api/client.ts`).

**Accounts on this device (switching).** One login = one Instagram account (its own client, email and password); the browser remembers up to 5 logins (`MAX_DEVICE_LOGINS`) so the person switches without a password. `lib/device-logins.ts` (pure, `tests/device-logins.test.ts`): the list `{ login id, user id, token, last used }` lives in one httpOnly cookie `lge_device_logins` sealed with AES-256-GCM under a key derived from `AUTH_SECRET` (never localStorage); the DB keeps `RememberedLogin` (token SHA-256, `sessionVersion`, 90-day sliding `expiresAt`). `lib/server/device-logins.ts`: `rememberLogin()` after log in / sign up / own password change (admins aren't remembered; a full device drops the least recently used), `listDeviceAccounts` (prunes logins that stopped working; a signed-in session not yet remembered gets remembered), `switchDeviceLogin` (`signIn("remembered")` — the second Credentials provider in `auth.ts`, whose `authorize()` accepts only a login in the request's own sealed cookie that passes `rememberedLoginProblem` via `lib/auth/remembered.ts`; refused → 409 `login_expired` and forgotten; not on this device → 404), `forgetDeviceLogin` (active one → 409 `login_active`), `logOutOfDevice` (one → next remembered login, else signed out; all → cookie + rows gone). Growth signals are computed in code (`computeGrowthSignals`, pure, `lib/analysis/growth-signals.ts`: shares from the shareability data, saves, comments and reach by post type, reach by weekday/time; ≥ 4 posts with reach and a ≥ 20 % lift; impact and rank set in code) and added to `gatherAssistantFacts(…, "strategy")` as "## Growth signals"; no signal → no AI call, 409 `recommendations_not_enough_data`. `AIService.strategy` writes one tip per signal; `parseStrategy` (`lib/services/text/strategy.ts`) drops a tip with a number not in the data (`tipUsesOnlyGivenNumbers`) or a Why that doesn't quote its signal; the mock writes the tips in code (`mockStrategyTips`). `lib/server/recommendations.ts` skips the AI when `strategyInputHash` (data by the day + past decisions + signals + `STRATEGY_PROMPT_VERSION`) matches the last run (an `unchanged` run) and stores `RecommendationRun` + `Recommendation` (`impact`, `rank`). Owner decisions are fed into the next prompt; Done stores a 14-day baseline and after 7 days `compareOutcome` stores up / down / no clear change / not enough data (reach, interactions, followers, shares, saves, comments). One set of tips a week: the daily cron (`GET /api/cron/daily`; `/api/cron/recommendations` runs only this part) analyses businesses whose last run is ≥ 7 days old (`RECOMMENDATIONS_CRON_BATCH`) and checks due outcomes; a manual Refresh within 7 days of the last analysis that produced tips → 409 `recommendations_week_set` (`refresh.nextSetAt`; unchanged checks and failures don't start a week), plus the safety net of 3 AI analyses per 24 h → 429 `recommendations_limit`; AI failure → 503 `recommendations_unavailable`, nothing changes; no Instagram data → 409 `instagram_not_connected`. Tests: `tests/growth-signals.test.ts`, `tests/gemini/strategy.test.ts`, `tests/e2e/recommendations.spec.ts` (Gemini stub) and `recommendations-mock.spec.ts` (`E2E_AI_PROVIDER=mock`). Cron routes share `assertCronAuthorized` (`lib/server/cron.ts`).

**Reply queue.** Engagement → `ReplyQueue` (`components/engagement/reply-queue.tsx`), one per tab by `kind` (`replyKind()`: AI comment drafts on Comment replies, AI DM drafts on DM replies, keyword drafts on Keyword replies — one cached list, filtered in the view): tabs Waiting / Sent; the as-is summary (`ReplySummaryCard`) is on Reply settings. Tap a reply to edit it (counter + Instagram's limits from `lib/replies.ts`: comment replies 300 chars / 4 hashtags / 1 link, DMs 1,000), Send or Cancel; Regenerate (AI drafts only, optional tone shorter / formal / friendly) is `POST /api/reply-drafts/:id/regenerate` → `AIService.rewriteReply()` (never template text from Gemini: 503 `regenerate_unavailable`, `REPLY_REGENERATE_LIMIT` 30/h per business → 429 `regenerate_limit`, plus the text request gate); `textAvailability()` (gate `peek()`) disables Regenerate up front, editing and sending always work. `ReplyDraft.aiReply` keeps what the AI (or keyword rule) proposed; on send `outcome` (AS_IS / EDITED / MANUAL, `replyOutcome()`) and `sentAt` are stored, shown in Sent with `GET /api/reply-drafts/summary`. Learning from edits: `replyStyleExamples()` (`lib/server/replies.ts`) puts up to 3 recent edited AI drafts into the reply prompt (`<edited_drafts>`), anonymised by `pickEditExamples()` (customer name/handle, greeted names, mentions, emails, phones → placeholders; the customer's message never goes in). Replies that can't be sent any more stay in Waiting with a warning until removed: EXPIRED (DM window) and UNAVAILABLE (comment deleted — Meta not_found / mock comment ids containing "deleted" → 409 `comment_unavailable`). All new AI reply requests go through `replyRequestBase()`.

**Analysis (competitors, methods, post performance).** Numbers are computed in code, pure and tested (`lib/analysis/`: `posts.ts` account stats — frequency, format mix, averages, best posts, weekday / part of day in the business timezone, hashtags, `compareAccounts`, `weeklyGrowth`; `methods.ts` rule-based `ruleMethod`, `rankMethods`, `promotedVsOrganic`; `post-performance.ts` `postVsAverage`, `postSeries`, `recentSummary`). AI text (EN+AR) is only an explanation on top: `AIService.competitorInsight` / `classifyPosts` / `postInsight`, prompts in `prompts.ts`, data blocks + parsers in `lib/services/text/analysis.ts` (any number not in the data rejects the answer; "measured vs estimated", correlation-not-causation wording); mock returns `not_configured`; a failure never hides the numbers (`AiTextState` "unavailable"). Caches: `CompetitorAnalysis` (by `inputHash` of posts + rounded numbers, so unchanged competitors aren't re-analysed), `PostInsight`, `PostMethod` (source RULE/AI/USER — the client's choice is never overwritten; `promoted` flag set by the client, no Ads API). The page loads numbers first and asks for the AI text separately (`AiExplanation`, `components/analysis/shared.tsx`; limits `COMPETITOR_INSIGHT_LIMIT`, `POST_INSIGHT_LIMIT`, `METHODS_AI_LIMIT` → 429 `analysis_limit`, plus the text gate). Daily cron (`runAnalysisSweep`, also `GET /api/cron/analysis` alone): `PostSnapshot` per recent post per day, method suggestions, weekly competitor lookup → `CompetitorSnapshot` (growth over time) and `Competitor.lookupIssue` (private / not_business / not_found) → comparison only when the numbers changed. Features (ON in every plan, migration `…_analysis`): `competitors.analysis` (`/competitors/analysis`), `postInsights` (`/post-performance`, `/post-performance/[id]`), `methods` (`/methods`). Competitors per plan: `DEFAULT_PLAN_LIMITS` (5) overridden by `SystemSetting "planLimits"` (admin System page), `competitorLimit()`. The assistant's Analytics/Competitors modes get these numbers via `gatherAssistantFacts(…, { permissions })`. Mock posts and the seed's history live in `mock-data/posts.ts`.

**Shareability ("Most shared").** Sub-feature `postInsights.shareability` (ON in every plan; migration `…_shareability` added the rows and the `ShareFindings` cache). Share rate = shares ÷ reach from the post insights already synced into `InstagramMedia.insights` (Meta: FEED posts and REELS support both; `fetchPostInsights` falls back to `reach,saved,shares` before `reach,saved`); posts reached by fewer than `SHARE_MIN_REACH` (100) are left out, the average is pooled (all shares ÷ all reach), "Most shared" needs `SHARE_MIN_POSTS` (3), patterns `SHARE_MIN_POSTS_FOR_PATTERNS` (6) — all pure in `lib/analysis/shareability.ts` (`tests/shareability.test.ts`). `lib/server/shareability.ts`: `GET /api/shareability` (numbers + cached findings), `POST /api/shareability/findings` (`AIService.shareFindings`: 1–3 EN+AR findings from `shareabilityDataBlock`, invented numbers rejected; the mock writes them in code from `sharePatterns`; rewritten at most once a day, retried an hour after a failure, `SHARE_FINDINGS_LIMIT`), the share rate on the post detail (`PostDetailDto.shareRate`, only with the feature). UI: `MostSharedCard` / `ShareRateCard` (`components/analysis/most-shared.tsx`); no share data → "Not available yet", never a banner. Daily cron (`runShareabilitySweep`, before Recommendations): post-insights-only sync for Meta accounts (`syncInstagram` scope `postInsights`, doesn't count as a sync) + findings. Recommendations get `shareabilityFactLines` (numbers + cached findings) and the share signal (`computeGrowthSignals`). Tests: `tests/e2e/shareability.spec.ts`.

**Home (removed).** The old Home dashboard (profile header, metrics, follower chart, top post, quick tiles, AI status card) is gone with `/api/dashboard*`; `/dashboard` and `/post-generator` redirect to `clientHome()` (query kept), so old links never 404. **Notifications.** Feature module `notifications`. Every feature calls `notify()` (`lib/server/notifications.ts`): it checks the client's modules and each user's `notificationPrefs`, stores one `Notification` per recipient (read state per user; `dedupeKey` keeps one live row per recurring subject, `renotifyAfterMs` limits re-alerts) and hands the rows to the delivery channels — in-app only today; email is a future `NotificationChannel` (`emailedAt`). Types, their preference, modules and page: `lib/notifications.ts` (`NOTIFICATION_TYPES`); text from `notifications.types.<type>` in the locales. Events: recommendations ready (weekly run), weekly report, Instagram reconnect (`meta-client` when a token is revoked + the daily check), scheduled post published/failed (cron only; they link to the Gallery while Posts is hidden), replies waiting (`notifyRepliesWaiting` after DM/comment/keyword drafts). The bell (`components/notifications/notification-bell.tsx`) polls `/api/notifications` every minute. Settings → Notifications lists only the types whose modules are on.

**Weekly reports.** Feature module `reports`, `/reports`. `lib/server/reports.ts` computes the week vs the week before in code (`computeWeeklyNumbers`, pure in `lib/services/text/report.ts`: complete UTC days, totals/averages/engagement/follower change/top and weakest post, `quality.demo`/`thin`), asks `AIService.weeklySummary()` for a short EN+AR summary of those numbers only (`parseReportSummary` rejects any number not in the data), and publishes with numbers only when the AI is unavailable. Generated by the daily cron (`GET /api/cron/daily`: reconnect alerts → reports → recommendations, AI calls spaced by `aiPace()` to `GEMINI_TEXT_RPM`, `REPORTS_CRON_BATCH`).

**Roles & proxy.** `proxy.ts` wraps Auth.js `auth()`. Logged-out → `/login` (public: `/login`, `/signup`, `/forgot-password`, `/reset-password`; `/verify-email` works either way); users can't open `/admin/*`; admins are sent to `/admin` unless the `lge_preview` cookie is set ("Preview as this client"), in which case user routes render that client.

**Feature permissions.** `config/features.ts` is the single catalogue (`FEATURE_KEYS`, `FEATURE_MODULES`). Keys are `module` or `module.sub`; a sub-feature is effective only if its module is ON (`isFeatureEnabled` in `lib/permissions`). Plan presets are in `config/plans.ts` (UI uses lowercase `starter`/`admin`; the DB enums are uppercase — map at the boundary). OFF features must be **removed, never grayed out**:
- nav: `filterNav()` over `config/navigation.ts` (`feature` on each page; a section without visible pages is removed and links to its first visible page)
- widgets: `<Feature flag>` / `useFeature()`
- routes: `await requireFeature(flag)` in the server page → `notFound()` (rendered by `app/(user)/not-found.tsx`)
- storage: one `FeaturePermission` row per (business, key); the session carries effective keys; the user layout builds the nav on the server and passes `permissions` to `ActiveClientProvider`

**Client state.** Server state lives in the TanStack Query cache (keys in `qk`, `lib/api/queries.ts`); mutations update it optimistically where it feels instant (reply approve/dismiss, rule toggles, permission toggles, removals) and roll back on error. User-screen mutations go through `useAction()`, which turns every action into a read-only notice during admin preview; in preview the data hooks read `/api/admin/preview/:id` instead of the user APIs. Failed mutations are reported centrally by `QueryProvider` via `reportError()` (`lib/api/errors.ts`): friendly localized `errors.<code>` toasts, the Connect Instagram dialog for `instagram_not_connected`, and a redirect to `/login?expired=1` on any 401 (`lib/api/client.ts`); pass `meta: { handlesErrors: true }` when a form shows its own errors. Toasts/prompt state: `store/ui-store.ts` (`notify.*`). Theme is **light by default**: only an explicit saved "dark" is dark (missing or the old "system" value reads as light, `normalizeTheme` in `lib/theme-script.ts`); the `lge_theme` cookie (set at login and on every toggle) drives the server-rendered `<html class>` and `THEME_INIT_SCRIPT` before first paint. Theme, language and sidebar state sync to `User.uiPreferences` through `PreferencesSync` (mounted in both shells); the login action sets the locale cookie from the saved language. Zustand selectors must not return fresh objects (`?? []` inside a selector causes an infinite render loop) — default outside the selector.

**i18n / RTL.** All UI copy is in `locales/en.json` + `locales/ar.json` (keep keys in sync), read via `useI18n().t("a.b", { var })`. Locale lives in the `lge_locale` cookie; the root layout sets `<html lang dir>`. Use logical properties (`ms-`, `pe-`, `start-`, `text-start`) and `<bdi>` for user content inside UI strings. Mock *content* (captions, comments) stays in its original language.

## Design system

Instagram-native look. All tokens live in `app/globals.css`: raw `--lge-*` variables (light on `:root`, dark on `.dark`), mapped in `@theme inline` to utilities such as `bg-background`, `text-muted`, `border-border`, `bg-primary` (#0095F6), `text-body` (14px) / `text-caption` (12px) / `text-title` / `text-heading`, `rounded-card` / `rounded-button` / `rounded-panel` / `rounded-pill`, `bg-ig-gradient`, `text-ig-gradient`. Use tokens, not raw hex. Keep the Instagram gradient to accents only. If you add a custom token, also register it in the `extendTailwindMerge` config in `lib/utils.ts`; otherwise `cn()` drops conflicting classes (e.g. `text-body` would remove `text-primary`).

**Avatars.** Every avatar goes through `components/shared/avatar.tsx` (`src` + initials/tone fallback when the image is missing or fails). Entities carry `avatarUrl` (`User`, `Client`, `Competitor`, `IncomingComment.authorAvatarUrl`). Images are local SVGs in `public/avatars/`, generated by `node scripts/generate-avatars.mjs` (brand marks and abstract silhouettes — no photos of real people, no hotlinking).

**Header.** The client header (`components/shell/top-bar.tsx`, Instagram-style) shows the business identity (the device-login switcher), the Instagram connection status, the notification bell and the profile avatar only (Settings → Instagram also has the status, followers and posts); the plan, language and dark/light switches are in the profile menu (`components/layout/profile-menu.tsx`, `menu-language` / `menu-theme`), which on phones also links any section that doesn't fit the tab bar (`shortcuts` = `splitForPhone().more`; Settings is always in the menu). Users have no "Profile" item (it only led back to the dashboard).

**Navigation.** `USER_NAV` in `config/navigation.ts` is the single source: the proposal's sections — Gallery (`/gallery`, home), Engagement (`/engagement/comments`, `/engagement/messages`, `/engagement/keywords`, `/engagement/settings` — Comment replies / DM replies / Keyword replies / Reply settings, each with a `descriptionKey`; `/engagement` redirects to the first visible tab so old links (`replies_waiting` notifications) keep working; views in `components/engagement/engagement-view.tsx`, each opening with an intro sentence and its automation's on/off status; Reply settings' Auto-reply switch is hidden by `SHOW_AUTO_REPLY = false` in `config/engagement.ts` because nothing sends AI replies on its own yet — the route and saved `BrandVoice.autoReply` stay), Insights (`/post-performance`, `/recommendations`, `/reports`, `/methods`, `/post-monitoring`, `/experiment` — "how am I doing" → "what to do" → deeper tools; each tab has a one-line `descriptionKey` under `nav.tabHints`; `/statistics` is hidden by `SHOW_STATISTICS = false` in `config/insights.ts` and redirects to Post performance, whose "What works best" card took its post-type/weekday bars), AI (`/ai`, between Engagement and Insights so it is the centre tab), Competitors (`/competitors`), Settings (`placement: "bottom"`, `mobile: false`; at the bottom of the sidebar and in the profile menu). Each section lists its `pages`; pages keep their own URLs. Sidebar (`components/layout/sidebar.tsx`, the platform's Instagram sidebar as before the proposal port, `from="lg"`: icon rail 1024–1279px, 244px from 1280px unless collapsed) = one row per section (active on any of its pages, `isActiveItem` in `lib/navigation.ts`), AI in an Instagram-gradient tile, then at the bottom Settings, the collapse button and the profile row (opens the profile menu with Log out); fixed bars beside it use `CLIENT_FIXED_START`, the main column `CLIENT_CONTENT_INSET`; below 1024px the phone tab bar (`components/shell/tab-bar.tsx`) = icons only with aria-labels, first `MAX_PHONE_TABS` (5) sections, AI as the gradient centre pill; `SectionTabs` (`components/layout/section-tabs.tsx`) shows a section's pages as tabs above the page when it has more than one. To add a page (Statistics, Post monitoring…), add one `pages` entry (a tab) or one section; `tests/navigation.test.ts` checks every page has a route and EN/AR labels.

**Sidebar collapse.** Both shells (`components/layout/sidebar.tsx`): state on `<html data-sidebar="collapsed">`, set before paint by `SIDEBAR_INIT_SCRIPT` (`lib/sidebar-script.ts`) from localStorage; style widths with the `sidebar-collapsed:` variant. The Next dev badge is disabled in `next.config.ts` because it covered the sidebar.
