@AGENTS.md

## Project

AI Growth Engine (shown to users; code, repo, DB and cookie names keep "local growth" / `lge_`) — Instagram growth/management app for local businesses (Raid Technologies). Next.js 16 + PostgreSQL/Prisma + Auth.js; every screen reads and writes through the JSON API with TanStack Query. Instagram data, AI generation and file storage sit behind swappable service interfaces with mock/local implementations until those integrations land. See README.md for setup and the real-vs-mocked list.

## Commands

- `npm run db:up` — start PostgreSQL (docker-compose.yml); `cp .env.example .env` first
- `npm run db:migrate` — apply/create migrations (`prisma migrate dev`); `npm run db:seed` — wipe + seed demo data; `npm run db:reset` — both
- `npm run dev` — dev server (http://localhost:3000)
- `npm run build` / `npm start` — production build / serve
- `npm run lint` — ESLint (flat config, includes React Compiler rules such as `react-hooks/set-state-in-effect`)
- `npx tsc --noEmit` — typecheck. Run `npx next typegen` first on a fresh clone; `LayoutProps` / `PageProps` globals are generated.
- Prisma 7: client is generated to `lib/generated/prisma` (gitignored; `postinstall` runs `prisma generate`), CLI config in `prisma.config.ts`, connection via `@prisma/adapter-pg`. Import the client from `@/lib/db` only.
- `npm run test:e2e` — Playwright (`tests/e2e/*.spec.ts`) starts its own `next dev` (port `E2E_PORT`, default 3001; never reuses a running server) on a seeded throwaway DB (`DATABASE_URL` must be local and named `*e2e*`/`*test*`; `E2E_BROWSER_CHANNEL=chrome`; see `playwright.config.ts`). The e2e server always runs with mock Instagram and the local Gemini stub, overriding `.env`.
- `npm run backfill-gallery-uploads` — one-off: earlier onboarding / brand-post uploads into the Gallery (dry run; `-- --apply`; a hosted DB also needs `--production`; DEPLOY.md). Runs with `tsx --conditions=react-server` so it can use `lib/server`.
- `npm test` — node:test + tsx over `tests/**/*.test.ts` (Meta mapping/client tests against `tests/meta/fixtures.json`). Test modules import only pure code (no `server-only`, no db).
- Run `next build` / `next dev` from the correctly-cased project path (on Windows): a lowercase cwd loads Next's internals twice and every page fails prerender with "Expected workStore to be initialized".

## Architecture

**Data flow.** Server pages in `app/` only guard (`requireFeature()` / `requireAdmin()`, → `notFound()`/redirect) and render a client `*View` from `components/<feature>/`. Views load data with the hooks in `lib/api/queries.ts` (user screens) and `lib/api/admin.ts` (admin), each with an Instagram-style skeleton, `ErrorState` and `EmptyState` (`components/shared/states.tsx`). The (user) layout renders the business view model (`getClientView()`, `lib/server/client-view.ts`) into `ActiveClientProvider`; after changing the business itself (photo, Instagram connection) call `router.refresh()`. Nothing under `app/`, `components/` or `lib/api` may import `/mock-data` — only the mock services, the seed and the front-end-only Gallery / AI chat (`mock-data/gallery`, see below) do.

**Auth.** Auth.js v5 (`auth.ts` at the root): Credentials provider + bcryptjs, JWT session in an httpOnly cookie. Session claims (`role`, `businessId`, `name`, `avatarUrl`, effective `features`, `sessionVersion`) live in the JWT. On **every** request the `jwt` callback runs `checkSession` (`lib/auth/claims.ts`, one PK lookup): deleted/suspended users and tokens whose `sessionVersion` differs are signed out; claims reload when `User.updatedAt` or `Business.permissionsUpdatedAt` is newer than the token (5-min safety refresh otherwise). Any code that changes a business's `FeaturePermission` rows must bump `permissionsUpdatedAt` (`lib/server/permissions.ts` does); any password change must go through `setPassword()` (`lib/server/passwords.ts`), which bumps `sessionVersion`. `authorize()` rate-limits failed logins (5 / 15 min per IP + email) through the `RateLimiter` interface (`getRateLimiter()` in `lib/server/rate-limit.ts`, in-memory; `RATE_LIMIT_STORE` selects the implementation) and throws `CredentialsSignin` subclasses whose `code` the login form shows. `lib/auth/actions.ts`: login, logout, start/exit admin preview. Login is one field + password: a username or the email of an older account (`parseIdentifier`, `lib/usernames.ts`: an "@" means email). **No email is sent by the app** (verification, reset and the Resend provider are gone): there is no self-service password reset — an admin sets a client's password (`POST /api/admin/users/:id/reset-password { password }` → `setPassword()`, the "Set password" item on the client page's Logins card). Demo logins live in `config/demo.ts` (used by the seed and the login page).

**API (`app/api`).** Every route is wrapped in `handler()` (`lib/server/http.ts`): JSON envelope `{ ok: true, data }` / `{ ok: false, error: { code, message, details? } }`, `ApiError` for expected failures, Zod via `readJson` / `readQuery` / `readParams`. Guards in `lib/server/guards.ts`: `requireAuth`, `requireRole("ADMIN" | "USER")`, `requireBusiness`, `requireFeature(...keys)` / `requireAnyFeature` / `assertFeature` — a disabled feature is **404**, never 403. The businessId always comes from the session (or an admin route param), never from the body; lookups by id use `where: { id, businessId }` so other businesses' rows are 404. Queries use the explicit `*_SELECT` constants + mappers in `lib/server/dto.ts` so hashes/tokens are never loaded. Business-scoped reads live in `lib/server/data.ts` (shared by user routes and `/api/admin/preview/:id`); log changes with `logActivity()`. Response types: `types/api.ts`. Browser calls: `apiFetch` (`lib/api/client.ts`).

**Services (`lib/services`).** Interfaces with env-selected implementations: `InstagramService` — chosen **per connection** (`InstagramConnection.provider`, routed in `getInstagramService()`): `MockInstagramService` serves the mock packs by business id; `MetaInstagramService` (`lib/services/instagram.meta.ts`) reads data synced into the DB by `lib/server/instagram-sync.ts` and calls Meta live only for replies, business discovery and publishing (see **Publishing** below). Instagram DMs arrive at `/api/webhooks/instagram` (GET handshake with `META_WEBHOOK_VERIFY_TOKEN`; POST verified with `X-Hub-Signature-256` + `META_APP_SECRET`, 200 at once, work in `after()`): `lib/server/instagram-dm.ts` finds the business by `igAccountKey` (mock: `igUserId`), respects `engagement.aiReplies`, stores `InstagramDirectMessage` and keeps one PENDING `ReplyDraft` (channel `DM`) per conversation; approval sends via `replyToMessage` (`lib/services/meta/messaging.ts`, `POST /me/messages`), 24-hour window → `EXPIRED` / `dm_window_closed`; `npm run simulate-dm` signs a fake webhook for local testing. Keyword replies (`engagement.dmRules`, `EngagementRule` + `KeywordReplyTrigger`): the same webhook's `comments` changes, with the sync as fallback, go through `lib/server/keyword-replies.ts` (pure matching/decision in `lib/keyword-replies.ts`): the trigger row (unique per comment) is the dedupe claim, 24-hour per-person cooldown, public reply via `replyToComment` + private DM via `sendPrivateReply` (`recipient: { comment_id }`), approval-mode rules create a `ReplyDraft` with `ruleId`/`privateReply`; reply drafts are gated per kind (`replyKinds` in `lib/server/replies.ts`); `npm run simulate-comment`. `INSTAGRAM_PROVIDER` (`mock`|`meta`) only picks the flow for new connections (`connectFlow()`, `lib/services/meta/config.ts`). Pure Meta code lives in `lib/services/meta/` (config, Graph client with appsecret_proof + usage headers + backoff, error classification, mappers, endpoint functions — tested in `tests/meta/`); Facebook Login is `lib/server/meta-connect.ts` + `app/api/integrations/instagram/*`; per-business Graph clients (`graphFor`, `lib/server/meta-client.ts`) log failures to `IntegrationEvent` and flag the connection (190 → `NEEDS_RECONNECT`, permission → `missingPermissions`). Clients see a reconnect banner only for an expired/revoked token; missing permissions are just a "Permissions missing" tag on Settings → Instagram (Reconnect there re-requests them); the admin integration card lists them. Map service errors with `instagramApiError()` (`lib/server/instagram-errors.ts`). Write calls need a connection → `instagram_not_connected`; `AIService` (`lib/services/ai.ts`, `AI_PROVIDER` `mock`|`gemini`; mock fills caption templates from `catalog.ts`; `GeminiAIService` never fails — on any error it returns the mock's text and logs the reason to IntegrationEvent (provider "gemini", call `ai.*`); every prompt is in `lib/services/text/prompts.ts`, pure client/parsing/request gate (`GEMINI_TEXT_RPM` 12/min, `GEMINI_TEXT_RPD` 450/day per instance — over budget → template text, logged once; pauses after quota/key errors) in `lib/services/text/`, tested in `tests/gemini/text.test.ts`), `ImageService` (`lib/services/image.ts`, `IMAGE_PROVIDER` `mock`|`gemini`; pure Gemini client, error classification, prompt builder and mock PNG in `lib/services/images/`, tested in `tests/gemini/` with recorded fixtures — never call Google in tests; `GEMINI_API_BASE` points the client at a local stub) — Post Generator draft images (`lib/server/post-images.ts`: generate / upload / remove, one image per draft, `PostDraft.imageSource` GENERATED gets the "AI-generated image" label, failures are `image_unavailable` with a reason, logged to IntegrationEvent with provider "gemini"); `StorageService` (`STORAGE_PROVIDER`: `local` disk in `UPLOAD_DIR`, served by `/api/uploads/[...key]`; `vercel-blob` = `lib/services/blob-storage.ts`, pure with an injected Blob client, tested in `tests/storage/`; `spaces` = private DigitalOcean Spaces, `lib/services/spaces-storage.ts` (S3 API, injected client/presigners, tested in `tests/storage/spaces.test.ts`): files are kept as `/api/files/<key>` (the route checks the business in the key `b/<businessId>/…` — pass `businessId` to `save()` for a business's content — and redirects to a signed link, `SPACES_URL_TTL`), Gallery uploads use a presigned POST (ticket mode `presigned`), Instagram gets a signed link when a container is made (`instagramImageUrl` in publishing); shared contract in `storage-core.ts`), The Post Generator's product catalogue comes from `catalog.ts` (mock). Instagram tokens are AES-256-GCM encrypted (`lib/crypto.ts`); `getInstagramAccount()` decrypts server-side only.

**AI keys (admin).** Gemini keys are set in the admin panel: the platform key on the System page ("AI settings", `GET/PUT/DELETE /api/admin/ai-settings`) and an optional per-client key on the client page (`/api/admin/businesses/:id/ai-key`, overrides the platform key for that business; removing it goes back). `AiKey` rows (`scopeKey` "platform" / "business:<id>" / reserved "plan:<PLAN>", `provider`, reserved `model`) hold the key encrypted with `lib/crypto.ts` (AES-256-GCM, `ENCRYPTION_KEY`) and only `last4` is ever sent to the browser; `AiKeyEvent` + `ActivityLog` (`ai_key.set` / `ai_key.cleared`) record who and when, never the key. `resolveGeminiKey(businessId)` (`lib/server/ai-keys.ts`, 15 s cache, pure order in `lib/services/ai-key-core.ts`) gives client key → plan key (later) → platform key → `GEMINI_API_KEY`; `GeminiAIService.run` / `textAvailability(businessId)` and `GeminiImageService.generate({ businessId })` use it, and the text request gate is kept **per key** (`gates` keyed by the key's fingerprint, Redis namespace `gemini:<fingerprint>`). Saving needs a valid `ENCRYPTION_KEY` (32 bytes, base64; `encryptionKeyProblem()`): without it `PUT` answers 503 `encryption_not_configured` and the card shows a warning (the app never reads `TOKEN_ENCRYPTION_KEY`). Admin-created logins (`POST /api/admin/users`, "New client" → owner) take a username with the email optional (`resolveIdentity`, `assertIdentityFree`). "Test key" = `POST /api/admin/ai-keys/test` (one small call with the typed key, else the key in use; 10/min per admin). UI: `components/admin/ai-key-card.tsx`. Tests: `tests/ai-keys.test.ts`, `tests/e2e/admin-ai-keys.spec.ts`.

**Accounts on this device (switching).** One login = one Instagram account (its own client, email and password); the browser remembers up to 5 logins (`MAX_DEVICE_LOGINS`) so the person switches without a password. `lib/device-logins.ts` (pure, `tests/device-logins.test.ts`): the list `{ login id, user id, token, last used }` lives in one httpOnly cookie `lge_device_logins` sealed with AES-256-GCM under a key derived from `AUTH_SECRET` (never localStorage); the DB keeps `RememberedLogin` (token SHA-256, `sessionVersion`, 90-day sliding `expiresAt`). `lib/server/device-logins.ts`: `rememberLogin()` after log in / sign up / own password change (admins aren't remembered; a full device drops the least recently used), `listDeviceAccounts` (prunes logins that stopped working; a signed-in session not yet remembered gets remembered), `switchDeviceLogin` (`signIn("remembered")` — the second Credentials provider in `auth.ts`, whose `authorize()` accepts only a login in the request's own sealed cookie that passes `rememberedLoginProblem` via `lib/auth/remembered.ts`; refused → 409 `login_expired` and forgotten; not on this device → 404), `forgetDeviceLogin` (active one → 409 `login_active`), `logOutOfDevice` (one → next remembered login, else signed out; all → cookie + rows gone). A remembered login stops working when logged out of/removed (row deleted), on a password change (`setPassword()` deletes the rows; `sessionVersion` mismatch), suspension/deletion, or expiry. Routes: `GET /api/device-accounts`, `POST /api/device-accounts/switch`, `DELETE /api/device-accounts/:id`, `POST /api/device-accounts/logout { all? }`; every transition is a full page load (`lib/api/device-accounts.ts`: `logOutOf`, `openAddAccount`), switching lands on `/dashboard?switched=1` (the user shell shows "Switched to @handle"). "Add account" opens `/login?add=1` or `/signup?add=1` (proxy lets signed-in clients through). UI: `LoginSwitcher` (`components/layout/login-switcher.tsx`, a bottom sheet on phones; `ActiveAccountSwitcher` picks it or the old one by `LOGIN_HAS_SEVERAL_ACCOUNTS`), "Log out of @handle" / "Log out of all accounts" there and in the profile menu. `requireAuth` refuses a request whose `x-lge-account` isn't the active account (409 `account_switched`), so a tab of the previous login can't read or act for the new one. Tests: `tests/e2e/device-accounts.spec.ts`.

**Instagram accounts under one login (turned off).** `LOGIN_HAS_SEVERAL_ACCOUNTS = false` in `config/accounts.ts` hides its switcher, "Add account", `/api/accounts*`, the admin client card and the System page's "Instagram accounts per login"; code and tables stay so it can come back (`tests/e2e/accounts.spec.ts` skips while off). What follows describes it: one login can belong to several Instagram accounts — each is its own `Business` with its own data. `BusinessMember` (user ↔ business) lists them; `User.businessId` is the **active** account (migration `20261016090000_instagram_accounts` backfilled one membership per existing user; deleting a business sets it to null, never deletes the login). The session's `businessId` is checked against the memberships on every request (`checkSession` → `resolveActiveAccount`, `lib/accounts.ts`), so every guard and query stays scoped to the active account; notifications are per (user, account). The user layout renders `<meta name="lge-account">`; `apiFetch` sends it as `x-lge-account` and `requireBusiness` answers 409 `account_switched` when it isn't the active one (a stale tab reloads into Home). `lib/server/accounts.ts`: `listAccounts` (unread per account), `switchAccount` (non-members → 404), `addAccount` (`source ACCOUNT_ADDED`, copies plan + permissions, then the onboarding wizard; over `PlanLimits.instagramAccounts` (default 1, admin System page, `accountLimitFor`) → 409 `account_limit`), `adminAccountsFor` (admin client page card). Routes: `GET/POST /api/accounts`, `POST /api/accounts/switch`, `GET /api/admin/businesses/:id/accounts`. UI: `AccountSwitcher` (`components/layout/account-switcher.tsx`) at the top of the client header and in the wizard header when the login has other accounts. Connecting an Instagram account the login already has → `already_added`. Background jobs work per business and never read the active account. UI copy says "Instagram accounts", never "businesses". Tests: `tests/accounts.test.ts`, `tests/e2e/accounts.spec.ts`.

**Self-onboarding.** Sign-up is one page, and no account exists until Instagram is connected. `/signup` (username, password, "Continue with Instagram"; server action `signupAction` → `startInstagramSignup`, `lib/server/signup.ts`) validates (`usernameProblem`, `lib/usernames.ts`: 3–30 characters, English letters, numbers, `_` and `.`, unique without regard to case — stored lower case in `User.username`) and stores a `PendingSignup` (bcrypt hash only, 15 min, one per username — starting again replaces it; the username is kept as the row's placeholder email); only its id goes into the encrypted httpOnly `lge_signup` cookie and the OAuth state (`su.<id>.<nonce>`, the row keeps the nonce's SHA-256). Then Facebook Login (`buildDialogUrl`), or with `INSTAGRAM_PROVIDER=mock` the demo screen `/signup/demo-instagram`; both come back to `/api/integrations/instagram/callback` (token mode: `/token`), which hands sign-up states to `finishInstagramSignup`: cookie/state/row must match and not be expired, then connect (`grantAndPages(null, …)` in `meta-connect.ts`; several accounts → picker on `/signup` via `/api/signup/pending`), refuse an account connected elsewhere (`taken`), and only then create user + business (`source SELF_SIGNUP`, `onboardingStatus IN_PROGRESS`, plan from `SystemSetting "selfSignupPlan"`, `lib/server/settings.ts`, named after Instagram) + connection in one transaction, sign in through the Auth.js `signup` provider (one-time ticket, `lib/auth/signup-ticket.ts`), remember the login → `/onboarding`. Every feature calls `notify()` (`lib/server/notifications.ts`): it checks the client's modules and each user's `notificationPrefs`, stores one `Notification` per recipient (read state per user; `dedupeKey` keeps one live row per recurring subject, `renotifyAfterMs` limits re-alerts) and hands the rows to the delivery channels — in-app only today; email is a future `NotificationChannel` (`emailedAt`). Types, their preference, modules and page: `lib/notifications.ts` (`NOTIFICATION_TYPES`); text from `notifications.types.<type>` in the locales. Events: recommendations ready (weekly run), weekly report, Instagram reconnect (`meta-client` when a token is revoked + the daily check), scheduled post published/failed (publishing jobs from the cron or Gallery "Post now", not the old inline "Publish now"; they link to the Gallery while Posts is hidden), replies waiting (`notifyRepliesWaiting` after DM/comment/keyword drafts). The bell (`components/notifications/notification-bell.tsx`) polls `/api/notifications` every minute. Settings → Notifications lists only the types whose modules are on.

**Weekly reports.** Feature module `reports`, `/reports`. `lib/server/reports.ts` computes the week vs the week before in code (`computeWeeklyNumbers`, pure in `lib/services/text/report.ts`: complete UTC days, totals/averages/engagement/follower change/top and weakest post, `quality.demo`/`thin`), asks `AIService.weeklySummary()` for a short EN+AR summary of those numbers only (`parseReportSummary` rejects any number not in the data), and publishes with numbers only when the AI is unavailable. Generated by the daily cron (`GET /api/cron/daily`: reconnect alerts → reports → recommendations, AI calls spaced by `aiPace()` to `GEMINI_TEXT_RPM`, `REPORTS_CRON_BATCH`).

**Roles & proxy.** `proxy.ts` wraps Auth.js `auth()`. Logged-out → `/login` (public: `/login`, `/signup`); users can't open `/admin/*`; admins are sent to `/admin` unless the `lge_preview` cookie is set ("Preview as this client"), in which case user routes render that client.

**Feature permissions.** `config/features.ts` is the single catalogue (`FEATURE_KEYS`, `FEATURE_MODULES`). Keys are `module` or `module.sub`; a sub-feature is effective only if its module is ON (`isFeatureEnabled` in `lib/permissions`). Plan presets are in `config/plans.ts` (UI uses lowercase `starter`/`admin`; the DB enums are uppercase — map at the boundary). OFF features must be **removed, never grayed out**:
- nav: `filterNav()` over `config/navigation.ts` (`feature` on each page; a section without visible pages is removed and links to its first visible page)
- widgets: `<Feature flag>` / `useFeature()`
- routes: `await requireFeature(flag)` in the server page → `notFound()` (rendered by `app/(user)/not-found.tsx`)
- storage: one `FeaturePermission` row per (business, key); the session carries effective keys; the user layout builds the nav on the server and passes `permissions` to `ActiveClientProvider`

**Client state.** Server state lives in the TanStack Query cache (keys in `qk`, `lib/api/queries.ts`); mutations update it optimistically where it feels instant (reply approve/dismiss, rule toggles, permission toggles, removals) and roll back on error. User-screen mutations go through `useAction()`, which turns every action into a read-only notice during admin preview; in preview the data hooks read `/api/admin/preview/:id` instead of the user APIs. Failed mutations are reported centrally by `QueryProvider` via `reportError()` (`lib/api/errors.ts`): friendly localized `errors.<code>` toasts, the Connect Instagram dialog for `instagram_not_connected`, and a redirect to `/login?expired=1` on any 401 (`lib/api/client.ts`); pass `meta: { handlesErrors: true }` when a form shows its own errors. Toasts/prompt state: `store/ui-store.ts` (`notify.*`). Theme is **light by default**: only an explicit saved "dark" is dark (missing or the old "system" value reads as light, `normalizeTheme` in `lib/theme-script.ts`); the `lge_theme` cookie (set at login and on every toggle) drives the server-rendered `<html class>` and `THEME_INIT_SCRIPT` before first paint. Theme, language and sidebar state sync to `User.uiPreferences` through `PreferencesSync` (mounted in both shells); the login action sets the locale cookie from the saved language. Zustand selectors must not return fresh objects (`?? []` inside a selector causes an infinite render loop) — default outside the selector.

**i18n / RTL.** All UI copy is in `locales/en.json` + `locales/ar.json` (keep keys in sync), read via `useI18n().t("a.b", { var })`. Locale lives in the `lge_locale` cookie; the root layout sets `<html lang dir>`. Use logical properties (`ms-`, `pe-`, `start-`, `text-start`) and `<bdi>` for user content inside UI strings. Mock *content* (captions, comments) stays in its original language.

**Kubernetes (DigitalOcean).** `DEPLOY-DIGITALOCEAN.md`, `Dockerfile` (targets `runner` — standalone output via `NEXT_OUTPUT=standalone`, non-root — and `migrate`), `k8s/` (kustomize: web + worker Deployments, CronJobs calling the worker's cron routes, migration Job, Ingress), `.github/workflows/docker-build.yml` (build + health check on every push) and `deploy-doks.yml` (manual, off until `DOKS_ENABLED`). Switches, all unset on Vercel: `STORAGE_PROVIDER=spaces`; `RATE_LIMIT_STORE=redis` (`REDIS_URL`, `lib/server/redis.ts`) shares the rate limits and the Gemini budget (`RedisRateLimiter` / `SharedTextGate` in `lib/services/redis-stores.ts`, in-memory fallback when Redis doesn't answer, `tests/redis-stores.test.ts`); `BACKGROUND_MODE=worker` makes "Post now" leave the job to the worker (its poller calls `/api/cron/publish` every 15 s). `/api/health` (liveness) and `/api/health?ready=1` (database), pure checks in `lib/health.ts`. `docker-compose.prod.yml` runs the image with Postgres, Valkey and MinIO.

## Design system

Instagram-native look. All tokens live in `app/globals.css`: raw `--lge-*` variables (light on `:root`, dark on `.dark`), mapped in `@theme inline` to utilities such as `bg-background`, `text-muted`, `border-border`, `bg-primary` (#0095F6), `text-body` (14px) / `text-caption` (12px) / `text-title` / `text-heading`, `rounded-card` / `rounded-button` / `rounded-panel` / `rounded-pill`, `bg-ig-gradient`, `text-ig-gradient`. Use tokens, not raw hex. Keep the Instagram gradient to accents only. If you add a custom token, also register it in the `extendTailwindMerge` config in `lib/utils.ts`; otherwise `cn()` drops conflicting classes (e.g. `text-body` would remove `text-primary`).

**Avatars.** Every avatar goes through `components/shared/avatar.tsx` (`src` + initials/tone fallback when the image is missing or fails). Entities carry `avatarUrl` (`User`, `Client`, `Competitor`, `IncomingComment.authorAvatarUrl`). Images are local SVGs in `public/avatars/`, generated by `node scripts/generate-avatars.mjs` (brand marks and abstract silhouettes — no photos of real people, no hotlinking).

**Header.** The client header (`components/shell/top-bar.tsx`, Instagram-style) shows the business identity (the device-login switcher), the Instagram connection status, the notification bell and the profile avatar only (Settings → Instagram also has the status, followers and posts); the plan, language and dark/light switches are in the profile menu (`components/layout/profile-menu.tsx`, `menu-language` / `menu-theme`), which on phones also links any section that doesn't fit the tab bar (`shortcuts` = `splitForPhone().more`; Settings is always in the menu). Users have no "Profile" item (it only led back to the dashboard).

**Navigation.** `USER_NAV` in `config/navigation.ts` is the single source: the proposal's sections — Gallery (`/gallery`, home), Engagement (`/engagement/comments`, `/engagement/messages`, `/engagement/keywords`, `/engagement/settings` — Comment replies / DM replies / Keyword replies / Reply settings; `/engagement` redirects to the first visible tab so old links (`replies_waiting` notifications) keep working; views in `components/engagement/engagement-view.tsx`, each opening with an intro sentence and its automation's on/off status; Reply settings' Auto-reply switch is hidden by `SHOW_AUTO_REPLY = false` in `config/engagement.ts` because nothing sends AI replies on its own yet — the route and saved `BrandVoice.autoReply` stay), Insights (`/insights`, `/post-performance`, `/recommendations`, `/reports`, `/methods`, `/post-monitoring`, `/experiment` — "how am I doing" → "what to do" → deeper tools; `/insights` is the Overview (UX3, `postInsights`, `components/insights/overview-view.tsx`, `GET /api/insights/overview`): three key numbers for the last 7 days vs the 7 before picked by the first onboarding target / aim, a percentage only with ≥ 3 posts each week and a big enough base, this week's Recommendations tips (`TipCard`), and a summary built in code with its sample size (pure `computeOverview` in `lib/analysis/overview.ts`, `tests/overview.test.ts`, `tests/e2e/insights-overview.spec.ts`); `/statistics` is hidden by `SHOW_STATISTICS = false` in `config/insights.ts` and redirects to Post performance, whose "What works best" card took its post-type/weekday bars), AI (`/ai`, between Engagement and Insights so it is the centre tab), Competitors (`/competitors`), Settings (`placement: "bottom"`, `mobile: false`; at the bottom of the sidebar and in the profile menu). Each section lists its `pages`; pages keep their own URLs. Sidebar (`components/layout/sidebar.tsx`, the platform's Instagram sidebar as before the proposal port, `from="lg"`: icon rail 1024–1279px, 244px from 1280px unless collapsed) = one row per section (active on any of its pages, `isActiveItem` in `lib/navigation.ts`), AI in an Instagram-gradient tile, then at the bottom Settings, the collapse button and the profile row (opens the profile menu with Log out); fixed bars beside it use `CLIENT_FIXED_START`, the main column `CLIENT_CONTENT_INSET`; below 1024px the phone tab bar (`components/shell/tab-bar.tsx`) = icons only with aria-labels (the sidebar's labels; every nav icon is drawn by `NavIcon`, `components/layout/nav-icon.tsx`, the only icon map — `tests/e2e/navigation.spec.ts` checks desktop and phone match), first `MAX_PHONE_TABS` (5) sections, AI as the gradient centre pill; `SectionTabs` (`components/layout/section-tabs.tsx`) shows a section's pages as tabs (labels only) above the page when it has more than one; the row scrolls sideways on phones, never the page. To add a page (Statistics, Post monitoring…), add one `pages` entry (a tab) or one section; `tests/navigation.test.ts` checks every page has a route and EN/AR labels.

**Sidebar collapse.** Both shells (`components/layout/sidebar.tsx`): state on `<html data-sidebar="collapsed">`, set before paint by `SIDEBAR_INIT_SCRIPT` (`lib/sidebar-script.ts`) from localStorage; style widths with the `sidebar-collapsed:` variant — the toggle's icon and label too, so they always match the width. This browser's saved state wins: `PreferencesSync` applies the account's `uiPreferences.sidebarCollapsed` (saved 600 ms after a toggle, so it can be stale after a quick reload) only on a browser with no saved state (`hasSavedSidebarState`). The Next dev badge is disabled in `next.config.ts` because it covered the sidebar.

`components/ui/` holds shadcn-style primitives on the unified `radix-ui` package, restyled. `components/shared/` holds the Instagram composites (`PostPreview`, `CommentRow`, `MetricCard`, `StatTile`, `FeatureToggle`, `ClientRow`, `Avatar` with story ring, `MediaPlaceholder` for mock imagery). Icons: lucide-react, 24px outline.
